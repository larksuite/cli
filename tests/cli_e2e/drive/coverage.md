## Summary
- TestDrive_FilesCreateFolderWorkflow: proves `drive files create_folder` in `create_folder as bot`; helper asserts the returned folder token and registers best-effort cleanup via `drive files delete`.
- TestDrive_StatusWorkflow: proves `drive +status` against a real Drive folder. Seeds the remote side via `drive +upload` (`unchanged.txt`, `modified.txt`, `remote-only.txt`), seeds local files with the matching/diverging contents, and asserts every output bucket (`unchanged`, `modified`, `new_local`, `new_remote`) holds exactly the expected `rel_path` and `file_token`. Cleans up uploaded files and the parent folder via best-effort cleanup hooks.
- TestDrive_UploadWorkflow: proves `drive +upload` against the real backend in both create and overwrite modes. First uploads a fresh file into a temporary Drive folder, then re-uploads new bytes with `--file-token` against the returned token, asserts the overwrite keeps the token stable, downloads the file with explicit `--output` to confirm the remote content changed, and downloads again without `--output` to prove default filename resolution saves the remote name with matching bytes.
- TestDriveDownloadDryRun_DefaultNamePlansMetadataBeforeDownload / TestDriveDownloadDryRun_ExplicitOutputSkipsMetadata: dry-run coverage for `drive +download`; asserts omitted `--output` plans metadata before download for default naming, while explicit `--output` preserves the direct download-only path.
- TestDrive_ImportWorkflow: proves `drive +import` against the real backend. It imports a temporary Markdown file as docx, waits for the async task when needed, verifies the returned document token, and deletes the imported document during cleanup.
- TestDrive_DuplicateRemoteWorkflow: proves the duplicate-remote workflows against the real backend. One subtest uploads two same-name files into the same Drive folder and asserts `drive +status` and default `drive +pull` both fail with a typed validation error for the duplicate rel_path, while `drive +pull --on-duplicate-remote=rename` succeeds, downloads both files, and writes a hashed renamed sibling locally. The other subtest uploads duplicate remote files, runs `drive +push --on-duplicate-remote=newest --if-exists=overwrite --delete-remote --yes`, and then re-runs `drive +status` to prove the mirror converged to a single unchanged `dup.txt`.

- TestDrive_UpdateTitleWorkflow: proves `drive +update-title` against the real backend. Uploads a file into a temporary Drive folder, renames it with an extension-preserving title, reads the title back through `drive +inspect`, then exercises both extension policies on the same file: default `keep` (title without extension gets `.txt` appended, `extension_appended`/`previous_title` reported, name verified) and `allow` (title submitted verbatim, extension dropped on purpose, no `previous_title` because the guard skips the read). Then renames the containing folder (token stays stable, so the cleanup hook still resolves it) and re-reads that title too. A final negative leg renames the file with `--type docx` and asserts the endpoint answers `981003` while the name stays untouched. Live-probed manually beforehand as user before the assertions were encoded: `type=docx` / `type=folder` / `type=file` / `type=wiki` renames, that `type=wiki` needs the wiki node token (the underlying document token returns `981003`), that wiki node and underlying docx titles stay in sync in both directions, that a `--type` mismatch and an unknown token share code `981003`, that a bot without edit permission gets `981004`, that an empty `new_title` is accepted by the server and blanks the title (hence the local `--title` guard), and that a `type=file` title without an extension drops the extension server-side (hence the extension guard). Error-scenario guidance was probed the same way rather than assumed: renaming a document the identity cannot edit returns `981004 forbidden` for both user and bot (a document-permission failure, not a scope one), a 25-request burst against the endpoint returns `99991400 request trigger frequency limit` (classified `api/rate_limit`, retryable) for the requests over the limit, and the platform's missing-scope shapes were read off a scope the app does not hold: `99991679` for a user token (envelope carries `missing_scopes` plus an `auth login --scope` hint) and `99991672` for an app scope that was never applied. Titles are stored verbatim — a `new_title` of `"  spaced title  "` reads back with both pads intact — which is why the CLI trims `--title` before sending it. `doc` and `mindnote` are listed by the platform metadata but refused by the backend: the service log for a real mindnote token records `unsupported update file type=mindnote` and answers `981002 params error` before any token lookup, and probes confirm the type is what fails — a real docx token renames fine under `--type docx` yet returns `981002` under `--type doc` or `--type mindnote`, while unknown tokens under supported types return `981003`. Both are therefore refused locally. Miaoda apps were probed the same way: `type=apps` is rejected by gateway field validation (`99992402`, the same answer a nonsense type gets) while a supported type with an unknown token answers `981003`, which is why the CLI rejects apps inputs and points at the apps domain instead of forwarding them. Rate-limit and scope failures are not asserted in the live workflow — one would need a deliberate burst, the other a second app — so their guidance is unit-tested against the codes instead.
- TestDrive_PullDryRun / TestDrive_PullDryRunAcceptsDuplicateRemoteStrategies: dry-run coverage for `drive +pull`; asserts the list-files request shape, Validate-stage safety guards, and acceptance of `--on-duplicate-remote=rename|newest|oldest` by the real CLI binary.
